## 一、简历条目

**RP-Harness：基于 LLM 的角色扮演 Agent Harness（个人项目）**

独立设计并实现了一个 LLM 应用运行时，在模型与用户之间加入确定性层管理记忆与交互，零第三方运行时依赖（Node.js 内置 fetch/WebSocket + 手写 RFC6455 协议层）。

- **上下文工程**：每轮按预算重裁上下文，只保留"人设+世界书+账本 → 剧情化摘要 → 近期原文"三层；超预算时由旁侧模型把最旧剧情压缩成保留专有名词与伏笔的前情提要，原文归档可检索。压测：1500 字符预算下 3 回合剧情稳定压入 350+ 字摘要，窗口恒不越界
- **结构化记忆账本**：回合结束后旁侧模型自动产出五分区（人物/物品/关系/伏笔/备注）JSON 增量，多写者按 key 合并去重，失败降级不阻断剧情；账本快照每轮注入 system
- **Agent 工具循环**：思考→工具→验证→再思考闭环，循环上限防死循环，工具执行错误回填给模型自我修正
- **决策卡交互**：模型通过 `decide` 工具在重大转折处暂停，把候选走向做成卡片交给用户选择，选择注入后剧情沿用户决定发展，全部留痕可回看
- **兼容生态**：SillyTavern v1/v2 JSON 角色卡、世界书关键词/常驻激活、思维链（reasoning_content）剥离——正文零污染
- **零依赖 Web 层**：手写 WebSocket（RFC6455 帧解析/掩码/心跳）与 Node http 服务，前端实现流式输出、决策卡、账本面板、角色卡上传
- 质量：19 个单元测试（mock LLM）全过，TypeScript 严格模式零错误

**技术栈**：TypeScript（Node.js ≥ 22）、OpenAI 兼容 API（streaming + function calling）、WebSocket、node:test

## 三、高频面试题

### 1. 什么是 harness？为什么角色扮演需要它？
Harness 是夹在模型和用户之间的运行时层，负责模型不擅长的事：记忆管理、上下文裁剪、工具调度、与用户交互。
普通聊天是"对话即上下文"，RP 场景下窗口被过程性内容（工具中间结果、思考链）塞满，且越聊越失忆。harness 每轮从架构层重新裁剪，只让模型看到叙事所需的最小集合——"确定性代码管记忆，模型只管写剧情"。

### 2. 上下文压缩策略怎么设计的？预算怎么分配？
预算 = 总预算 × 80%（预留 20% 给模型回复），减去 system 长度后为可用窗口。
窗口放不下时，从最旧回合开始：交给旁侧模型把"旧摘要 + 该回合用户输入 + 正文"合并成新的完整摘要（非增量），原文按 JSONL 归档。
摘要 prompt 显式要求保留专有名词和未回收伏笔，并限制字数；输出异常（过短）时保留旧摘要降级。

### 3. 记忆账本为什么用旁侧模型？失败怎么办？
主循环上下文要保持纯净单一，把记账塞进去会污染剧情。旁侧模型独立调用，输入"本轮输入+正文+旧账本"，输出结构化增量。
可靠性：解析失败/调用失败一律 catch，保留旧账本并打 warn，绝不抛异常阻断剧情；多写者（agent 工具 + 旁侧记账）按 key 合并去重。

### 4. 决策卡怎么实现的？
注册 `decide` 工具（question/options/allow_free_input schema）。harness 循环里拦截该工具名：解析卡片 → 通过回调（CLI readline / Web 卡片）暂停等用户 → 选择作为 tool 结果回填 → 模型带选择继续写。留痕写 `decisions.jsonl`。参数不合法会回填错误让模型自纠。

### 5. 手写 WebSocket 的难点？
HTTP Upgrade 握手（Sec-WebSocket-Accept = SHA1(key+GUID)）；帧解析：FIN/opcode、126/127 长度、客户端掩码异或、分包 buffer 管理；text/continuation/close/ping-pong 处理。用 Node 内置 WebSocket 客户端 + 真实浏览器双重验证。

### 6. 思维链怎么处理？
deepseek 返回独立 `reasoning_content`。流式时只累计不回调（客户端看不到），非流式同理剥离。正文永远是模型输出原样——harness 不改写正文（"修音可以，假唱不行"）。

### 7. 怎么防死循环？
`maxLoopTurns` 上限（默认 10），模型反复调同一工具也会在 N 次调用后终止；同时工具错误回填让模型有机会自纠而非卡死。

### 8. 多写者账本合并冲突？
每条目带 `key`，合并时按 key 更新/追加，同名不堆积。多写者（agent 工具写、旁侧记账写）共用同一个 merge 入口。

### 9. 怎么测试 LLM 系统？
单元测试全部 mock LLM（脚本化返回 tool_calls/正文），覆盖：解析、合并、裁剪触发、循环上限、错误回填、决策拦截；真实验证走演示脚本 + 浏览器端到端，控制 token 成本。

### 10. 与 LangChain / SillyTavern / Liyuan 的区别？
LangChain 是通用 agent 框架；本项目聚焦 RP 场景的确定性记忆与交互，零依赖、结构小而清晰。
兼容 SillyTavern 的数据生态（角色卡/世界书/预设的 JSON 格式）但独立实现解析，不使用其代码。
Liyuan 是同类项目（启发思路：上下文裁剪、账本、决策卡），本项目为独立实现，代码全部自研。

### 11. 项目局限？（主动说，加分）
记账/压缩与主剧情共用一个模型（未做模型分级）；世界书用关键词匹配而非向量检索；token 估算为字符启发式；未做多会话隔离与鉴权（单机自用）；角色卡仅支持 JSON（未解析 PNG 内嵌卡）。
